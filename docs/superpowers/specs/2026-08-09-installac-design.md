# Design: /installAC — portable AC pipeline skills, installable per project

**Date:** 2026-08-09
**Status:** Draft for review

## Goal

Make the Auto Claude-style pipeline skills (currently hand-written and
Kinetix-specific in `kx2/kx_repo/.claude/`) **generic and installable into any
project** via a bot command: `/installAC <path>`. Installed projects get an
attended pipeline (run from any Claude session, including bridge sessions) and
an unattended one (ralph loop), with project specifics isolated in a small
bindings file.

## Architecture

Three layers:

1. **Vendored templates** (this repo, `templates/ac-pipeline/`) — the canonical,
   generic skill set. Versioned here like the vendored ralph scripts.
2. **Per-project install** (`<project>/.claude/`) — a copy of the templates plus
   a generated `ac-bindings.md` capturing the project's answers. Committed to
   the project so worktrees and teammates get it.
3. **The installer** (`/installAC` bot command) — copies templates, asks setup
   questions via inline keyboard, writes bindings, commits.

### Layer 1: the generic skill set

`templates/ac-pipeline/` contains:

```
skills/ac-pipeline/SKILL.md      # the adaptive pipeline (see below)
skills/ac-review/SKILL.md        # PR/MR review against project standards
skills/ac-investigate/SKILL.md   # pre-work triage with code evidence
skills/ac-ideate/SKILL.md        # 3-lens improvement discovery
commands/ac.md                   # /ac <ticket-or-goal>
commands/ac-review.md            # /ac-review <target>
commands/ac-investigate.md       # /ac-investigate <ticket-or-description>
commands/ac-ideate.md            # /ac-ideate <area>
bindings.template.md             # -> .claude/ac-bindings.md at install
ralph-prompt.template.md         # -> plans/prompt_tasks.md (optional)
```

**`ac-pipeline`** is the kx `jira-ac-pipeline` with every Kinetix binding
replaced by a reference to the bindings file: adaptive complexity rubric
(simple/medium/complex), mini-spec for complex, Plan subagent → checkboxed
`plan.md`, subtask implementation loop, fresh-QA-subagent loop (cap 3),
Status-header resume protocol. Artifacts under **`.acp/<task-id>/`**
(generic replacement for `.jiraAC/`), gitignored.

New vs the kx version — an **Operating modes** section defined once, in the
generic skill:

- **Attended** (default): ask at gates (ambiguity, plan approval, posting
  externally, ship).
- **Unattended** (must be explicitly stated by the invoking prompt, e.g. the
  ralph prompt): ambiguous task → skip and report, never guess; QA cap
  reached → leave branch + findings, move on; terminus is the bindings' ship
  action (default: raise PR); **never** performs the bindings'
  "done-transition" (e.g. DevVerified/close issue) — that is always human.

All four skills reference intake/ship/review mechanics only via the bindings
file — no tracker names hardcoded.

### Layer 2: the bindings file

`bindings.template.md` → `.claude/ac-bindings.md`, generated from install
answers:

```markdown
---
name: ac-bindings
description: Project bindings for the AC pipeline skills — tracker, branching, ship policy. Generated by /installAC v<N>; edit freely.
---

- **Tracker**: jira | github | none
  - jira: intake via `jira` MCP tools (`jira_get_issue`, `jira_search`); the
    project must have the server registered.
  - github: intake via `gh issue view/list`.
  - none: /ac takes a described goal; task-id is a slug.
- **Base branch**: <e.g. develop | main> — always `git fetch origin` and
  branch from `origin/<base>`.
- **Ship policy**: pr | push-only | direct-merge (+ PR target branch,
  reviewer notes)
- **Done-transition**: <what marks a task done, e.g. a Jira transition, issue
  close, or "none"> — attended-only, never unattended.
- **Standards docs**: <optional paths the plan/QA/review phases must read>
```

Skills read this file at Phase 0; if it's missing they stop and tell the user
to run `/installAC` (or write one by hand — it's just markdown).

### Layer 3: the /installAC command

New `src/handlers/commands/installac.ts`, registered like `/ralph`:

- `/installAC <path>` — path resolves like ralph's (`Working dir` setting
  base, `~` expansion); must be an existing git repo. Rejects if a dirty
  `.claude/ac-bindings.md` exists with un-answered upgrade (see below).
- Copies `templates/ac-pipeline/` skills+commands into `<path>/.claude/`,
  appends `.acp/` to the project `.gitignore` (idempotent).
- Asks, via inline keyboard in the chat (grammY `InlineKeyboard`, callback
  branches in `callback.ts` following the existing `ralph:`/`skill:`
  prefixes, prefix `acinstall:`):
  1. Tracker? [Jira] [GitHub] [None]
  2. Base branch? [main] [develop] [type…]
  3. Ship policy? [PR] [Push only] [Direct merge]
  4. Install unattended ralph prompt? [Yes] [No]
- Writes `ac-bindings.md` from the template + answers; if Q4 = Yes, writes
  `plans/prompt_tasks.md` from `ralph-prompt.template.md` (each ralph
  iteration: next task from tracker → run ac-pipeline **unattended** →
  signal).
- Commits everything in the target repo:
  `"Install AC pipeline skills (ac-pipeline v<N>) via /installAC"`.
- **Upgrade path**: template files carry `<!-- ac-pipeline-version: N -->`.
  Re-running `/installAC` on an installed project overwrites skill/command
  files (they're vendored, not user-owned), **preserves `ac-bindings.md`**,
  and reports old→new version. Bindings are the user's; templates are ours.

### Ralph integration (unattended pipeline)

No bridge-code changes needed: `/ralph <path>` already prefers the repo's
`plans/prompt_tasks.md`. The installed ralph prompt + the skill's unattended
mode section is the whole integration. `/ralph stop`, watchdog, beats all
work as-is.

## Security / safety

- The installer only ever writes to the target repo the user named; no
  network actions.
- Unattended mode's hard rules live in the generic skill: never guess on
  ambiguity, never perform done-transitions, terminus = ship policy.
- Bindings never contain credentials — tracker access rides on whatever MCP
  servers/CLIs the project already has.

## kx_repo migration (deferred — v2)

kx_repo keeps its four bespoke skills unchanged for now. Once /installAC has
proven itself on another project, migrate kx_repo by installing the generic
set with jira/develop/PR bindings pointing at kinetix-repo-jira-access +
kx-raise-pr, and delete the bespoke pipeline skill. Not part of this build.

## Testing

- Unit: template copy + gitignore idempotency + bindings generation from
  answer sets + version-stamp upgrade logic (existing test layout under
  `src/__tests__/`).
- Manual: install into a scratch git repo from Telegram, run `/ac` attended
  on a "none"-tracker goal; run `/ralph` on the same repo for one iteration.

## Build order

1. Templates (the four generic skills + command files + bindings/ralph
   templates) — pure markdown, testable by hand-copying into a scratch repo.
2. Installer command + callbacks + registration.
3. Upgrade path + tests.
